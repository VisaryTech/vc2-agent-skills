# 1С:Бухгалтерия 3.0 через OData

Скилл читает справочники и создаёт контрагентов, поступления товаров/услуг и полученные счета-фактуры. Документы записываются без проведения; изменение и удаление не поддерживаются.

Вход — нормализованный JSON для УПД, ТОРГ-12, актов и счетов-фактур. Извлечение из XML/PDF/сканов, корректировки и возвраты выполняются отдельно. Требуется Python 3.10+, сторонних зависимостей нет.

## Настройка

Команды выполняются из каталога скилла. Доступ задаётся через окружение; `.env` автоматически не загружается.

```bash
export ONEC_ODATA_URL='https://host.example/base/odata/standard.odata/'
export ONEC_ODATA_USERNAME='ai_accountant'
read -rsp 'Пароль: ' ONEC_ODATA_PASSWORD
export ONEC_ODATA_PASSWORD
python3 scripts/onec_odata.py check
python3 scripts/onec_odata.py discover
```

| Переменная | Назначение |
| --- | --- |
| `ONEC_ODATA_URL` | Корневой OData URL без query, fragment и встроенных credentials |
| `ONEC_ODATA_USERNAME` | `ai_accountant` |
| `ONEC_ODATA_PASSWORD` | Пароль |
| `ONEC_ODATA_ALLOW_HTTP` | `1` разрешает HTTP тестовой базы; по умолчанию требуется HTTPS |
| `ONEC_ODATA_STATE_DIR` | Каталог вне репозитория; по умолчанию `~/.local/state/onec-odata` |

Проверка TLS включена, redirects запрещены. Пользователю нужны права чтения справочников/документов и создания контрагентов, поступлений и счетов-фактур.

В каталоге состояния для каждой публикации хранятся схема, профиль, журналы операций и HTTP-логи. Права файлов — 0600, каталога — 0700. В журналы попадают ID, этапы, хеш входа и статусы; пароль и тела документов не сохраняются.

## Профиль базы

`discover` читает `$metadata`, сохраняет `metadata.json` и создаёт `profile-template.json`. Скопируйте шаблон в `profile.json` и заполните фактическими именами сущностей и полей. Другой путь задаётся глобальным аргументом `--profile FILE`.

Metadata описывает схему, но не подтверждает право создания. Семантику реквизитов и значения перечислений сверяйте с EnumType и данными базы. После проверки профиля задайте `reviewed: true`. Изменение `metadata_sha256` блокирует работу до обновления профиля.

| Поле профиля | Содержимое |
| --- | --- |
| `version`, `reviewed`, `metadata_sha256` | `1`, `true`, хеш из discovery |
| `roles` | Роли из таблицы ниже; каждая содержит `entity_set` и `fields`: логическое поле → свойство CSDL |
| `defaults` внутри роли/таблицы | Дополнительные постоянные скалярные реквизиты, не пересекающиеся с `fields` |
| `required_on_create` внутри роли | Физические поля, обязательные при создании; серверные автозаполняемые поля исключаются |
| `vat_rates` | Входная ставка → значение 1С; допустимы `none`, `0`, `5`, `7`, `10`, `18`, `20`, `22` |
| `counterparty_kinds` | `supplier.kind` → значение `fields.kind` |
| `receipt_kinds` | `upd`/`torg12`/`act` → значение `fields.document_kind`; также допускается словарь `goods`/`services`/`mixed` по составу строк |

| Роль | Обязательные логические поля | Дополнительные поля |
| --- | --- | --- |
| `organizations` | `id`, `code`, `inn`, `kpp` | `name` |
| `counterparties` | `id`, `inn`, `kpp`, `name` | `kind` |
| `contracts` | `id`, `code`, `organization`, `supplier` | `name` |
| `items`, `units` | `id`, `code` | `name`; у `items` также `unit`, `is_service`, `is_folder` |
| `currencies` | `id`, `code` | `name`; роль нужна при использовании валютной ссылки |
| `receipts` | `id`, `organization`, `supplier`, `number`, `date`, `total`, `posted`, `includes_vat` | `contract`, `currency`, `vat_total`, `document_kind`, `document_date`, `is_upd` |
| `invoices` | `id`, `organization`, `supplier`, `number`, `date`, `posted` | `basis` либо `basis_table`; также `contract`, `currency`, `total`, `vat_total`, `document_date` |

У всех ролей доступно поле `deletion_mark`: помеченные на удаление ссылки отклоняются. `number`/`date` обозначают реквизиты входящей первички поставщика, а `document_date` — внутреннюю дату документа 1С. `is_upd` заполняется по типу входа.

Сущности должны иметь единственный GUID-ключ. Ссылки — `Edm.Guid`, суммы/количества — `Edm.Decimal` или `Edm.Double`, флаги — `Edm.Boolean`. Расчёты выполняются через `Decimal`; для Double отправляются JSON-числа без промежуточного float.

У `receipts.tables` обязательны `goods` и `services`. Каждая таблица содержит:

- `property`: имя коллекции сложного типа из metadata;
- `fields`: `item`, `unit`, `quantity`, `price`, `amount`, `vat`, `vat_rate` и необязательный `line_no`;
- `amount_mode`: `net`, `gross` либо `input` — сумма без НДС, с НДС либо согласно `includes_vat`;
- `defaults`: дополнительные постоянные реквизиты строки.

Для услуг `unit` можно не сопоставлять, если поля нет в metadata. Единица всё равно читается из справочника; при `items.fields.unit` сверяется с номенклатурой. Одна таблица может обслуживать оба вида строк, если её описание одинаково.

Основание счёта-фактуры задаётся через `fields.basis` либо `basis_table` с `property`, `fields.basis`, необязательным `fields.line_no` и `defaults`. Для составной ссылки допускается UUID в `Edm.String`; дискриминатор типа задаётся в defaults.

Документ с таблицами создаётся одним POST. Если обязательные реквизиты нельзя выразить этим профилем или требуется последующее обновление, импорт останавливается.

## Команды

```bash
python3 scripts/onec_odata.py list organizations
python3 scripts/onec_odata.py list contracts --where '{"code":"SUPPLY-001"}'
python3 scripts/onec_odata.py list items --all
python3 scripts/onec_odata.py find-counterparty --inn 1234567890 --kpp 123456789
python3 scripts/onec_odata.py import /private/primary.json --dry-run
python3 scripts/onec_odata.py import /private/primary.json
python3 scripts/onec_odata.py operation-status 11111111-1111-4111-8111-111111111111
```

`list` принимает точные условия по логическим полям. По умолчанию возвращает до 100 записей; `--limit` — 1–10000, `--all` обходит пагинацию с пределом 100000 записей/10000 страниц. Результаты сверяются с фильтром.

Результаты и операционные ошибки — JSON в stdout. Коды выхода: 0 — успех, 2 — ожидаемая ошибка, 3 — внутренняя ошибка, 130 — прерывание. Ошибки аргументов CLI выводятся в stderr.

## Входной JSON

Пример УПД; коды справочников и применимую ставку НДС выбирайте для своей базы и операции:

```json
{
  "operation_id": "11111111-1111-4111-8111-111111111111",
  "type": "upd",
  "function": "invoice_transfer",
  "number": "UPD-001",
  "date": "2026-10-21",
  "organization": {"code": "ORG-001"},
  "supplier": {"inn": "1234567890", "kpp": "123456789", "name": "Поставщик"},
  "contract": {"code": "CONTRACT-001"},
  "currency": {"code": "643"},
  "includes_vat": true,
  "total": "120.00",
  "vat_total": "20.00",
  "lines": [{
    "kind": "goods",
    "item": {"code": "ITEM-001"},
    "unit": {"code": "UNIT-001"},
    "quantity": "2",
    "price": "60.00",
    "net": "100.00",
    "vat": "20.00",
    "gross": "120.00",
    "vat_rate": "20"
  }],
  "invoice": {"number": "SF-001", "date": "2026-10-21"}
}
```

- `operation_id` — постоянный UUID; даты — `YYYY-MM-DD`. Количества, цены и суммы — десятичные строки. Денежные суммы округляются по строкам до копейки, `ROUND_HALF_UP`; отрицательные значения не поддерживаются.
- `organization` выбирается по `id`, точному `code` или ИНН/КПП. Договор, валюта, номенклатура и единица — по ID либо точному коду. Договор должен принадлежать организации и поставщику.
- `supplier` ищется по ИНН/КПП. Для юрлица нужны 10 цифр ИНН и 9 цифр КПП; для ИП — 12 цифр ИНН без КПП. При отсутствии контрагента требуется `name`, при необходимости — `kind` из профиля. Другие справочники автоматически не создаются.
- Договор/валюту можно опустить, если это допускает профиль и конфигурация. Неоднозначные ссылки останавливают импорт.
- `torg12` содержит `goods`, `act` — `services`, `upd` — любой состав строк. УПД требует `function: transfer` без `invoice` либо `invoice_transfer` с `invoice`. У ТОРГ-12 и акта `invoice` необязателен.
- `includes_vat` определяет включение НДС в цену. Сверяются количество × цена, net + vat = gross, ставка, НДС и итоги строк. `none` и `0` различаются; расчётная ставка выражается базовой ставкой и `includes_vat: true`.
- Отдельный `type: invoice` содержит общие реквизиты, суммы и `basis: {"number":"...","date":"YYYY-MM-DD"}` либо `basis: {"id":"UUID"}`. Поля `lines`, `includes_vat`, `function`, вложенный `invoice` не допускаются. Организация, поставщик, суммы и указанные договор/валюта сверяются с основанием.

`--dry-run` читает данные и показывает предполагаемые создания, найденные ID и `pending_supplier`. В 1С и журнал операции не пишет; HTTP-лог сохраняется. Неизвестные ID нового поставщика/основания подставляются при записи. Предпросмотр может содержать коммерческие данные.

## Дубли и восстановление

Дубли ищутся по организации, поставщику, типу сущности, номеру и дате первички; у счёта-фактуры сверяется основание. Реквизиты, суммы и строки должны совпасть, иначе возвращается `duplicate_conflict`. Существующий документ возвращается без изменения, даже если уже проведён.

Журнал хранит этапы `counterparty`, `receipt`, `invoice` и полученные ID. Поступление и счёт-фактура создаются отдельно: при частичном успехе повторите тот же вход с тем же UUID. Клиент сверит сохранённые объекты и создаст недостающие. Изменённый вход с прежним UUID вызывает `operation_conflict`.

GET повторяется до трёх раз при сетевых сбоях и HTTP 429/502/503/504 с задержками 1/2/4 секунды. `Retry-After` свыше 60 секунд возвращается как `retry_later`. Таймаут — 30 секунд, лимит тела — 16 МиБ. POST автоматически не повторяется.

При `write_outcome_unknown` сохраните вход и журнал, выполните `operation-status` и повторите тот же импорт для сверки. Этап `sending` блокирует новый POST, пока создание не подтверждено. Если результат не установлен, выясните его в 1С с администратором: новый UUID или удаление журнала могут привести к дублю.

`created_unverified` содержит ID для повторного чтения. После явного отказа `rejected` можно устранить причину и повторить прежний вход.

`import.lock` блокирует параллельные импорты с одним каталогом состояния. После аварии удаляйте только lock, убедившись, что процесс завершён; журналы сохраняйте. От сторонних импортёров эта блокировка не защищает.

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

Интеграционный тест включается через `ONEC_ODATA_LIVE_TESTS=1` и `ONEC_ODATA_LIVE_FIXTURE=/private/input.json`. Файл содержит документы `goods` (`torg12`), `services` (`act`), `upd` (`invoice_transfer`), `invoice` к `goods` и необязательный `mixed_upd`. UUID операций должны различаться, номера — начинаться с `TEST-ONEC-`. У `goods` нужен отсутствующий поставщик с именем `TEST-ONEC-...`; остальные ссылки должны существовать. Для `invoice` укажите того же поставщика и `basis` с номером/датой `goods`. Тест создаёт записи и сохраняет их в базе.
