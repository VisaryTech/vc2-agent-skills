# 1С через стандартный OData

Скилл читает и изменяет опубликованные сущности по `$metadata`. Добавление справочника или документа в публикацию не требует изменения кода. Имена полей, типы и ключи берутся из текущей схемы базы; конфигурационный профиль не нужен.

Python 3.10+, сторонних зависимостей нет. Все примеры выполняются из каталога скилла.

## Подключение

```bash
export ONEC_ODATA_URL='https://host.example/base/odata/standard.odata/'
export ONEC_ODATA_USERNAME='integration_user'
read -rsp 'Пароль: ' ONEC_ODATA_PASSWORD
export ONEC_ODATA_PASSWORD
python3 scripts/onec_odata.py check
python3 scripts/onec_odata.py entities --search Номенклатура
```

`.env` автоматически не загружается. `ONEC_ODATA_USERNAME` принимает любой непустой логин; права задаются в 1С.

| Переменная | Назначение |
| --- | --- |
| `ONEC_ODATA_URL` | Корневой OData URL без query, fragment и встроенных credentials |
| `ONEC_ODATA_USERNAME`, `ONEC_ODATA_PASSWORD` | Учётная запись публикации |
| `ONEC_ODATA_ALLOW_HTTP` | `1` для HTTP тестовой базы; по умолчанию требуется HTTPS |

Проверка TLS включена; redirects и переходы за пределы публикации запрещены. Скилл не создаёт каталог состояния, файлы метаданных, логи, журналы или блокировки. Результаты возвращаются в stdout; входной JSON читается из указанного файла.

## Поиск схемы и чтение

```bash
python3 scripts/onec_odata.py entities --search Номенклатура
python3 scripts/onec_odata.py describe Catalog_Номенклатура
python3 scripts/onec_odata.py query Catalog_Номенклатура --where '{"Code":"000001"}' --select Ref_Key,Code,Description --order-by 'Code asc' --limit 100
python3 scripts/onec_odata.py get Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}'
```

Имена в примерах условные: выбирайте EntitySet, поля и типы из своей metadata. `describe` возвращает ключи, унаследованные реквизиты, вложенные типы и перечисления, навигацию и объявленные ограничения публикации. `discover` также показывает параметры функций, их возвращаемые типы и связи навигации. Действия не поддерживаются; для разрешённых виртуальных таблиц регистров есть отдельная команда `register`.

`query --where` — JSON точных условий, объединённых `and`. Физические поля проверяются по metadata; результаты сверяются с условиями. `--select` и `--order-by` принимают поля через запятую; сортировка — `asc` или `desc`. По умолчанию возвращается до 100 записей, `--limit` — 1–10000. `--all` обходит пагинацию с пределом 100000 записей/10000 страниц.

`--key` — JSON-объект всех ключевых полей, включая составные ключи. Поддерживаются строковые, GUID, числовые, логические и временные ключи соответствующих типов. Ключи и фильтры экранируются клиентом; произвольные URL и выражения фильтра не принимаются.

`discover` возвращает полную схему в поле `metadata`, её SHA-256 и число EntitySet. Каждая команда читает текущую `$metadata`; схема хранится только в памяти до завершения вызова.

```bash
python3 scripts/onec_odata.py discover
```

### Расширенные фильтры

`query` и `count` принимают `--filter` — JSON-дерево. Оно объединяется с `--where` через `and`.

```bash
python3 scripts/onec_odata.py query Document_ЗаказКлиента --filter '{"op":"and","args":[{"op":"ge","field":"Date","value":"2026-10-01"},{"op":"lt","field":"Date","value":"2026-11-01"}]}' --select Ref_Key,Date,Number
python3 scripts/onec_odata.py query Catalog_Номенклатура --filter '{"op":"contains","field":"Description","value":"Кабель"}' --select Ref_Key,Description
```

Сравнения: `eq`, `ne`, `gt`, `ge`, `lt`, `le`; строковые операции: `startswith`, `endswith`, `contains`. Узел содержит ровно `op`, `field`, `value`. Логические узлы содержат `op` (`and`, `or`, `not`) и массив `args`; для `not` нужен один аргумент, для `and`/`or` — хотя бы один. Максимум — 32 уровня пользовательского дерева и 1000 узлов, включая внутренний объединяющий узел и условия `--where`.

Тип значения определяется metadata: GUID и даты задаются строками, точные Decimal/Int64 могут задаваться строками. Упорядоченные сравнения допустимы для чисел, строк и дат, строковые функции — только для String. `null` разрешён в `eq`/`ne`; коллекции, вложенные объекты и произвольные выражения OData в фильтрах не поддерживаются. `contains` отправляется как OData 3.0 `substringof`.

Клиент проверяет строки ответа по всему фильтру. Поля условий автоматически включаются в серверный `$select` и убираются из результата, если пользователь их не выбирал. Строковая проверка в клиенте чувствительна к регистру; если сравнение сервера имеет другую семантику и возвращает несовпадающие строки, команда завершается с `invalid_response`.

### Представления, навигация и количество

```bash
python3 scripts/onec_odata.py query Document_ЗаказКлиента --select Ref_Key,Number,Контрагент_Key --presentations
python3 scripts/onec_odata.py query Document_ЗаказКлиента --select Ref_Key,Number --expand Контрагент
python3 scripts/onec_odata.py count Catalog_Номенклатура --where '{"DeletionMark":false}'
```

`--presentations` добавляет `$select=…,*____Presentation` (четыре подчёркивания); без явного `--select` сохраняются обычные поля через `*`. Можно выбрать отдельное `Поле____Presentation`, если базовое поле, его `_Key` или навигация объявлены в metadata. Представления доступны только для чтения.

`--expand` принимает список навигационных свойств первого уровня через запятую. Их типы разрешаются по metadata, включая Association и псевдонимы пространств имён. Вложенные пути и выражения в `--expand` не принимаются. Раскрытые объекты/коллекции сохраняются в исходной структуре ответа и включаются в результат даже при явном `--select`.

`count` отправляет `$top=0&$inlinecount=allpages` и возвращает `{"ok":true,"count":N}`. Поддерживаются формы счётчика `odata.count`, `@odata.count`, `d.__count` и `__count`. Если сервер счётчик не вернул, результат — `operation_not_supported`; клиент не заменяет подсчёт полной выгрузкой.

### Пагинация

По умолчанию используется `--pagination next-link`: клиент следует только серверным ссылкам продолжения. Без `nextLink` ответ считается завершённым; наличие дополнительных записей клиент не угадывает.

Для публикаций с поддержкой `$skip`, которые не возвращают ссылки продолжения, доступен явный режим:

```bash
python3 scripts/onec_odata.py query Catalog_Номенклатура --all --pagination skip --page-size 100 --order-by 'Description asc'
```

Он требует `--all` и ключи metadata; размер страницы — 1–10000, по умолчанию 100. Сортировка дополняется недостающими ключевыми полями. Смещение увеличивается на число полученных строк; чтение заканчивается после пустой страницы, поэтому короткая страница сама по себе не обрывает выгрузку. Если сервер возвращает `nextLink`, используйте обычный режим. Пределы — 100000 записей/10000 страниц. Все ссылки проверяются на принадлежность публикации.

Сортировка не обеспечивает снимок данных: конкурентные вставки, удаления и изменения могут приводить к пропускам или повторениям при `$skip`. Для публикаций, не поддерживающих нужные параметры, команда возвращает серверную ошибку; автоматического переключения режима нет.

### Регистры

Команда `register` читает срезы, остатки и обороты через опубликованные функции. Параметры и тип результата проверяются по metadata; произвольные функции не вызываются. Синтаксис и примеры — в [работе с регистрами](references/registers.md).

## Создание, изменение и удаление

Вход `create`/`update` — JSON-объект с физическими именами полей. Например, `/private/item.json`:

```json
{"Description":"Новое наименование"}
```

```bash
python3 scripts/onec_odata.py create Catalog_Номенклатура /private/item.json --dry-run
python3 scripts/onec_odata.py create Catalog_Номенклатура /private/item.json
python3 scripts/onec_odata.py update Catalog_Номенклатура /private/item.json --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
python3 scripts/onec_odata.py mark-deletion Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
python3 scripts/onec_odata.py delete Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
```

После проверки удалите `--dry-run` у выбранной операции. Обновление — PATCH только переданных реквизитов; ключи менять нельзя. Передача табличной части заменяет **все её строки**, отсутствие поля сохраняет его значение. Массовой записи по фильтру нет.

`mark-deletion` меняет Boolean-поле `DeletionMark`; `--value false` снимает пометку. Если поля нет, команда возвращает ошибку. `delete` — физический DELETE. Не все виды сущностей и публикации допускают все операции: явные запреты metadata проверяются локально, права и прикладные правила определяет 1С. HTTP 400/403/405 и другие серверные отказы возвращаются со статусом; содержимое серверной ошибки не выводится, чтобы не раскрывать секреты и данные.

Для сущностей с `Posted` создание принудительно задаёт `false`; перед изменением и удалением клиент читает объект и требует `Posted: false`. Документ с неопределимым признаком проведения блокируется. Проведение и отмена, действия OData, PUT и `$batch` не поддерживаются. Без версии объекта предварительное чтение не защищает от конкурентного изменения в другой сессии; правила доступа и конкуренции должны обеспечиваться также на стороне 1С.

### Версия объекта

Для `update`, `mark-deletion` и `delete` заголовок `If-Match` выбирается в порядке: явный `--if-match`, ETag предварительного GET, затем `DataVersion` объекта. Значение передаётся без изменения. Если версии нет, команда сохраняет прежнее поведение без защиты от конкурентного изменения; dry-run возвращает `concurrency_protected: false`. Он также показывает предполагаемые `headers`.

Если вход подготовлен по ранее прочитанному объекту, передайте именно его версию:

```bash
python3 scripts/onec_odata.py update Catalog_Номенклатура /private/item.json --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --if-match 'AAAAAAAAB9E=' --dry-run
```

Автоматическая версия защищает интервал между предварительным GET и записью внутри одного вызова; она не обнаруживает, что входной файл подготовлен по более старым данным. HTTP 412 возвращается как `concurrency_conflict`, без повторной записи: перечитайте объект и пересмотрите изменение. `--if-match '*'` проверяет существование, а не совпадение версии, поэтому dry-run не считает его защитой от потери изменений. Явная версия не отменяет запрета работы с проведёнными документами.

### Типы и проверка

Проверяются неизвестные поля, null, длина строк, диапазоны целых, Precision/Scale, вложенные структуры, коллекции и EnumType. GUID-реквизиты могут содержать нулевой GUID, если это допустимо в базе. Decimal передаётся точной строкой, Double/Single — JSON-числом без промежуточного float. Десятичные JSON-числа входного файла тоже читаются без потери точности; для Int64 допускается строка.

`Edm.DateTime` принимает дату или ISO datetime без смещения, например `2026-10-23T16:30:00.123456`. `Edm.DateTimeOffset` требует время и явное смещение, например `2026-10-23T16:30:00+03:00`; время не обнуляется. Дополнительно поддерживаются Binary (base64) и Time (длительность `PT…H…M…S`). Неподдерживаемые типы возвращают ошибку.

Пропущенный реквизит с `Nullable=false` не обязательно ошибка: его может заполнить сервер. Metadata не описывает все бизнес-правила; суммы, договоры, ссылки и обязательность бизнес-реквизитов в универсальном CRUD пользователь задаёт самостоятельно. Бизнес-проверки конкретного сценария выполняются отдельно от этого скилла.

## Результат записи и ошибки

| HTTP | Код ошибки |
| --- | --- |
| 401 | `authentication_error` |
| 403 | `access_denied` |
| 404 | `object_not_found` |
| 405 | `operation_not_supported` |
| 412 | `concurrency_conflict` |

Эти ответы означают отказ запроса и не повторяются. HTTP-статус сохраняется в `http_status`; ошибки записи также содержат контекст операции. Исходное тело серверной ошибки и непроверенные серверные сообщения не выводятся.

Создание, изменение и удаление выполняются одним HTTP-запросом записи; затем клиент проверяет результат через GET. Успех возвращает `entity_set`, `operation`, `key` и `status: complete`. Для создания ключ берётся из ответа сервера либо из payload, если все ключевые поля были заданы явно.

Если ответ записи потерян, ключ не получен или контрольное чтение не подтвердило результат, возвращается `write_outcome_unknown` с сущностью, операцией и известным ключом (`null`, если ключ неизвестен). Ошибка проверки после успешной отправки также считается неопределённым результатом записи. Отсутствие ключа не означает, что создание не состоялось.

Перед повтором сверьте объект через `get` либо найдите его через `query` по бизнес-реквизитам. Каждый новый вызов выполняет новую операцию: локальной дедупликации, журнала восстановления и блокировки параллельных клиентов нет. Повтор создания может привести к дублю. `--operation-id` и `operation-status` отсутствуют.

GET повторяется до трёх раз при сетевых сбоях и HTTP 429/502/503/504 с задержками 1/2/4 секунды. `Retry-After` свыше 60 секунд возвращает `retry_later`. POST/PATCH/DELETE автоматически не повторяются. Таймаут — 30 секунд, размер тела — до 16 МиБ.

`--dry-run` выполняет только чтение и валидацию и возвращает предполагаемый запрос. Он не создаёт файлы и не меняет 1С. Предпросмотр содержит данные payload.

Результаты и операционные ошибки — JSON в stdout. Коды выхода: 0 — успех, 2 — ожидаемая ошибка, 3 — внутренняя ошибка, 130 — прерывание. Ошибки аргументов CLI — в stderr.

## Проверки

```bash
python3 -m unittest discover -s tests -v
```

Автономные тесты проверяют произвольные сущности, типы и составные ключи, фильтры, представления, навигацию, счётчики, пагинацию, функции регистров, версии объектов, защиту документов, неопределённые результаты записи, отсутствие файловых операций, CLI и транспорт. Они не подключаются к 1С. Успех тестов не подтверждает права записи, бизнес-правила и совместимость новых возможностей с конкретной публикацией. Требуется стандартный OData 3.0 с JSON; Atom/XML и OData 4 не поддерживаются. Доступность отдельных параметров зависит от версии платформы и публикации.

Интеграционная проверка чтения включается через `ONEC_ODATA_LIVE_READ_TESTS=1` с переменными подключения из раздела выше. Она читает метаданные, до двух записей и объект по ключу; любые HTTP-методы, кроме GET, блокируются. Тест выбирает первую подходящую сущность с ключом; её можно задать через `ONEC_ODATA_LIVE_ENTITY`. Записи в базу не выполняются.
