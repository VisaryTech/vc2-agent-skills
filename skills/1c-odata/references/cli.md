# Справочник CLI 1С OData

Запускайте команды из каталога скилла либо по абсолютному пути к `scripts/onec_odata.py`.

## Проверка настроек и подключения

`check-env` проверяет настройки без сети: успех — `{"ok":true}`, ошибка — `configuration_error` с именами проблемных переменных, без значений. Остальные команды выполняют эту проверку автоматически. `check` подключается к публикации и читает metadata.

Проверка TLS включена; redirects и выход за пределы публикации запрещены. Входной JSON читается из файла.

## Поиск схемы и чтение

```bash
python3 scripts/onec_odata.py entities --search Номенклатура
python3 scripts/onec_odata.py describe Catalog_Номенклатура
python3 scripts/onec_odata.py query Catalog_Номенклатура --where '{"Code":"000001"}' --select Ref_Key,Code,Description --order-by 'Code asc' --limit 100
python3 scripts/onec_odata.py get Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}'
```

Имена в примерах условные: EntitySet, поля и типы берите из metadata. `describe` показывает ключи, унаследованные реквизиты, вложенные типы, перечисления, навигацию и ограничения публикации. `discover` возвращает полную схему в `metadata` (включая сигнатуры функций и связи навигации), её SHA-256 и число EntitySet. Каждая команда читает текущую `$metadata`. Действия не поддерживаются; для виртуальных таблиц регистров используйте `register`.

`query --where` — JSON точных условий, объединённых `and`. Физические поля проверяются по metadata; результаты сверяются с условиями. `--select` и `--order-by` принимают поля через запятую; сортировка — `asc` или `desc`. По умолчанию возвращается до 100 записей, `--limit` — 1–10000. `--all` обходит пагинацию с пределом 100000 записей/10000 страниц.

`--key` — JSON-объект всех ключевых полей, включая составные ключи. Поддерживаются строковые, GUID, числовые, логические и временные ключи соответствующих типов. Ключи и фильтры экранируются клиентом; произвольные URL и выражения фильтра не принимаются.

### Расширенные фильтры

`query` и `count` принимают `--filter` — JSON-дерево. Оно объединяется с `--where` через `and`.

```bash
python3 scripts/onec_odata.py query Document_ЗаказКлиента --filter '{"op":"and","args":[{"op":"ge","field":"Date","value":"2026-10-01"},{"op":"lt","field":"Date","value":"2026-11-01"}]}' --select Ref_Key,Date,Number
python3 scripts/onec_odata.py query Catalog_Номенклатура --filter '{"op":"contains","field":"Description","value":"Кабель"}' --select Ref_Key,Description
```

Сравнения: `eq`, `ne`, `gt`, `ge`, `lt`, `le`; строковые операции: `startswith`, `endswith`, `contains`. Узел содержит ровно `op`, `field`, `value`. Логические узлы содержат `op` (`and`, `or`, `not`) и массив `args`; для `not` нужен один аргумент, для `and`/`or` — хотя бы один. Максимум — 32 уровня пользовательского дерева и 1000 узлов, включая внутренний объединяющий узел и условия `--where`.

Тип значения определяется metadata: GUID и даты задаются строками, точные Decimal/Int64 могут задаваться строками. Упорядоченные сравнения допустимы для чисел, строк и дат, строковые функции — только для String. `null` разрешён в `eq`/`ne`; коллекции, вложенные объекты и произвольные выражения OData в фильтрах не поддерживаются. `contains` отправляется как OData 3.0 `substringof`.

Клиент проверяет строки ответа по всему фильтру. Поля условий автоматически включаются в серверный `$select` и убираются из результата, если пользователь их не выбирал. Строковая проверка в клиенте чувствительна к регистру; если сравнение сервера имеет другую семантику и возвращает несовпадающие строки, команда завершается с `invalid_response`.

### Представления, навигация и количество

```bash
python3 scripts/onec_odata.py query Document_ЗаказКлиента --select Ref_Key,Number,Контрагент_Key --presentations
python3 scripts/onec_odata.py query Document_ЗаказКлиента --select Ref_Key,Number --expand Контрагент
python3 scripts/onec_odata.py count Catalog_Номенклатура --where '{"DeletionMark":false}'
```

`--presentations` добавляет `$select=…,*____Presentation` (четыре подчёркивания); без явного `--select` сохраняются обычные поля через `*`. Можно выбрать отдельное `Поле____Presentation`, если базовое поле, его `_Key` или навигация объявлены в metadata. Представления доступны только для чтения.

`--expand` принимает навигационные свойства первого уровня через запятую; вложенные пути и выражения запрещены. Типы разрешаются по metadata, включая Association и псевдонимы пространств имён. Раскрытые объекты/коллекции сохраняют структуру ответа и включаются в результат даже при явном `--select`.

`count` отправляет `$top=0&$inlinecount=allpages` и возвращает `{"ok":true,"count":N}`. Поддерживаются формы счётчика `odata.count`, `@odata.count`, `d.__count` и `__count`. Если сервер счётчик не вернул, результат — `operation_not_supported`; клиент не заменяет подсчёт полной выгрузкой.

### Пагинация

По умолчанию `--pagination next-link` следует серверным ссылкам продолжения; без `nextLink` чтение завершено.

Для публикаций с `$skip` без ссылок продолжения:

```bash
python3 scripts/onec_odata.py query Catalog_Номенклатура --all --pagination skip --page-size 100 --order-by 'Description asc'
```

Режим требует `--all` и ключи metadata; размер страницы — 1–10000, по умолчанию 100. Сортировка дополняется ключами, смещение — числом полученных строк. Чтение заканчивается на пустой странице, не на короткой. Пределы `--all` действуют в обоих режимах. При наличии `nextLink` используйте обычный режим.

При `$skip` конкурентные изменения могут давать пропуски и повторы. Неподдерживаемые сервером параметры возвращают ошибку; автоматического переключения режима нет.

### Регистры

`register` читает срезы, остатки и обороты через разрешённые опубликованные функции, сверяя параметры и тип результата с metadata. Синтаксис — в [работе с регистрами](registers.md).

## Создание, изменение и удаление

Вход `create`/`update` — JSON-объект с физическими именами полей. Например, `/private/item.json`:

```json
{"Description":"Новое наименование"}
```

```bash
python3 scripts/onec_odata.py create Catalog_Номенклатура /private/item.json --dry-run
python3 scripts/onec_odata.py create Catalog_Номенклатура /private/item.json
python3 scripts/onec_odata.py update Catalog_Номенклатура /private/item.json --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
python3 scripts/onec_odata.py mark-deletion Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
python3 scripts/onec_odata.py delete Catalog_Номенклатура --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --dry-run
```

После проверки удалите `--dry-run` у выбранной операции. Обновление — PATCH только переданных реквизитов; ключи менять нельзя. Передача табличной части заменяет **все её строки**, отсутствие поля сохраняет его значение. Массовой записи по фильтру нет.

`mark-deletion` меняет Boolean-поле `DeletionMark`; `--value false` снимает пометку. Отсутствие поля — ошибка. `delete` — физический DELETE. Запреты metadata проверяются локально; права и прикладные правила определяет 1С.

Для сущностей с `Posted` создание принудительно задаёт `false`; изменение и удаление требуют прочитанного `Posted: false`. Неопределимый признак проведения блокирует запись. Проведение и отмена, действия OData, PUT и `$batch` не поддерживаются. Без версии предварительное чтение не защищает от конкурентных изменений; доступ и конкуренцию нужно обеспечивать также на стороне 1С.

### Двухэтапное создание поступления

Проверенный обход для «Поступления товаров и услуг» в диагностированной конфигурации: POST шапки → PATCH «Товаров» с идентификаторами, номерами строк и счетами учёта. Вложенный POST без идентификаторов и PATCH без `ИдентификаторСтроки` давали HTTP 500. Причина отдельно не установлена; на другие сущности запрет вложенного POST не распространяйте.

1. Через `describe` сверьте имена и типы полей шапки и строк.
2. Создайте шапку без «Товаров»: `create --dry-run`, затем `create`. Отдельным `get` подтвердите шапку и `Posted: false` до заполнения строк. При неизвестном результате следуйте [правилам проверки записи](#результат-записи-и-ошибки).
3. Подготовьте полный состав: новым строкам задайте уникальный ненулевой GUID `ИдентификаторСтроки`, последовательный `LineNumber` с 1 и нужные счета учёта. Существующие строки и их идентификаторы сохраняйте.
4. Выполните `update --dry-run`, затем `update` по ключу шапки; в обоих вызовах передайте через `--if-match` версию, по которой готовили состав, если она доступна.
5. Отдельным `get` сверьте состав, реквизиты строк, итоговые суммы и `Posted: false`. При ошибке PATCH проверяйте существующий объект, не создавайте шапку заново. Этапы не образуют транзакцию: если заполнение не подтверждено, сообщите ключ и проверенное состояние.

### Версия объекта

Для `update`, `mark-deletion` и `delete` значение `If-Match` выбирается без преобразования: явный `--if-match` → ETag предварительного GET → `DataVersion`. Без версии запись идёт без защиты от конкурентного изменения. Dry-run показывает `headers` и `concurrency_protected`.

Если вход подготовлен по ранее прочитанному объекту, передайте именно его версию:

```bash
python3 scripts/onec_odata.py update Catalog_Номенклатура /private/item.json --key '{"Ref_Key":"11111111-1111-4111-8111-111111111111"}' --if-match 'AAAAAAAAB9E=' --dry-run
```

Автоматическая версия защищает только интервал GET → запись внутри вызова. HTTP 412 — `concurrency_conflict`: перечитайте объект и пересмотрите изменение, автоматического повтора нет. `--if-match '*'` проверяет лишь существование; как и отсутствие версии, даёт `concurrency_protected: false`. Версия не отменяет запрета работы с проведёнными документами.

### Типы и проверка

Проверяются неизвестные поля, null, длина строк, диапазоны целых, Precision/Scale, вложенные структуры, коллекции и EnumType. GUID-реквизиты могут содержать нулевой GUID, если это допустимо в базе. Decimal передаётся точной строкой, Double/Single — JSON-числом без промежуточного float. Десятичные JSON-числа входного файла тоже читаются без потери точности; для Int64 допускается строка.

`Edm.DateTime` принимает дату или ISO datetime без смещения, например `2026-10-23T16:30:00.123456`. `Edm.DateTimeOffset` требует время и явное смещение, например `2026-10-23T16:30:00+03:00`; время не обнуляется. Дополнительно поддерживаются Binary (base64) и Time (длительность `PT…H…M…S`). Неподдерживаемые типы возвращают ошибку.

Пропущенное поле с `Nullable=false` может заполнить сервер. Metadata не описывает все бизнес-правила: суммы, договоры, ссылки и обязательные бизнес-реквизиты задаются и проверяются отдельно от универсального CRUD.

## Результат записи и ошибки

| HTTP | Код ошибки |
| --- | --- |
| 401 | `authentication_error` |
| 403 | `access_denied` |
| 404 | `object_not_found` |
| 405 | `operation_not_supported` |
| 412 | `concurrency_conflict` |

Эти ответы означают отказ запроса и не повторяются. HTTP-статус сохраняется в `http_status`; ошибки записи также содержат контекст операции. Исходное тело серверной ошибки и непроверенные серверные сообщения не выводятся.

Каждый вызов записи отправляет один запрос, затем проверяет результат через GET. Успех — `entity_set`, `operation`, `key`, `status: complete`. При создании ключ берётся из ответа либо payload со всеми ключевыми полями.

Потеря ответа, отсутствие ключа или неуспешная проверка дают `write_outcome_unknown` с сущностью, операцией и известным ключом (иначе `null`). В том числе `verification_error: verification_failed` не означает отказ записи: она могла пройти даже без полученного ключа.

Перед повтором отдельно прочитайте объект через `get`; без ключа найдите через `query` по бизнес-реквизитам. Сверьте переданные значения и строки. Подтверждённую запись не повторяйте. При неопределённости остановитесь и сообщите известный ключ (либо его отсутствие) и проверенное состояние. Новый вызов — новая операция; повтор создания может дать дубль.

GET повторяется до трёх раз при сетевых сбоях и HTTP 429/502/503/504 с задержками 1/2/4 секунды. `Retry-After` свыше 60 секунд возвращает `retry_later`. POST/PATCH/DELETE автоматически не повторяются. Таймаут — 30 секунд, размер тела — до 16 МиБ.

`--dry-run` выполняет только чтение и валидацию и возвращает предполагаемый запрос, не меняя 1С. Предпросмотр содержит данные payload.

Результаты и операционные ошибки — JSON в stdout. Коды выхода: 0 — успех, 2 — ожидаемая ошибка, 3 — внутренняя ошибка, 130 — прерывание. Ошибки аргументов CLI — в stderr.
