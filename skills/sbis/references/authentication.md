# Авторизация

Документация проверена 15.10.2026. На production 19.10.2026 проверены сервисная авторизация, получение организаций, список входящих поступлений и чтение карточек. Запись и сервисный вход на тестовом хосте не проверены.

## Программная проверка настроек

`check-env` вызывает `sbis_lib.auth.validate_env()` без сети, получения токена и обращения к его кэшу. Успех — `{"ok":true}`, код 0; ошибка — `{"ok":false,"error":"configuration_error","message":"…"}`, код 2. Оба результата выводятся в stdout, значения настроек не выводятся. При авторизации используется та же логика проверки обязательных параметров; прежний код `credentials_required` сохраняется. Существующий приоритет окружения над `.env` или `--env-file` одинаков для проверки и остальных команд.

## Инструкция для администратора

Шаги настройки приложения сверены с документацией Saby 19.10.2026. Для скилла нужны три постоянных параметра приложения: `SBIS_APP_CLIENT_ID`, `SBIS_APP_SECRET`, `SBIS_SECRET_KEY`. Токен доступа CLI получает самостоятельно; отдельной переменной для готового токена нет.

### 1. Добавь приложение и настрой права

Войди в кабинет СБИС/Saby с правами управления подключениями:

1. Открой «Настройки» → блок «Система» → «Безопасность» → «Подключения к Saby».
2. Добавь приложение, например «Codex — документы ЭДО», укажи описание и подходящий тип приложения для вашей интеграции.
3. При необходимости задай адрес внешней системы или исходящий IP сервера, с которого будет запускаться CLI. Это адрес клиента интеграции, а не адрес API СБИС.
4. Включи сервисный доступ. При варианте «С ограничением по правам» настрой доступ к нужным организациям и участкам ЭДО: чтение документов, а для работы с черновиками — создание и редактирование. Вариант «Разрешен полностью» предоставляет максимальный доступ; выбирай его только в соответствии с принятой у вас настройкой прав.
5. Выбери авторизацию «по сервисному ключу» и сохрани приложение.

Основание: [добавление внешнего приложения](https://saby.ru/help/integration/api/auth/add_app). Одноразовый пароль для этого CLI не подходит.

### 2. Получи три параметра

Открой сохранённую карточку приложения в «Подключениях к Saby»:

| Где взять значение | Куда записать |
|---|---|
| «ID подключения» / ID приложения (`app_client_id`) | `SBIS_APP_CLIENT_ID` |
| «Защищенный ключ» (`app_secret`): покажи и скопируй значение | `SBIS_APP_SECRET` |
| Ключ из файла, скачанного в строке авторизации по сервисному ключу (`secret_key`) | `SBIS_SECRET_KEY` |

Порядок получения описан в [справке по параметрам приложения](https://link.saby.ru/page/kbase_entity/3033991d-f3da-41b6-9b8b-4c719df25e5a?folderId=fe0094d9-c5d6-43f3-97d8-63eaaa4b4ab5). Копируй само значение сервисного ключа, а не имя скачанного файла. Все три параметра должны относиться к одному приложению и выбранной площадке.

### 3. Настрой CLI и проверь доступ

Для Linux/Bash создай приватный файл вне репозитория:

```bash
mkdir -p ~/.config/sbis
chmod 700 ~/.config/sbis
(umask 077; touch ~/.config/sbis/sbis.env)
chmod 600 ~/.config/sbis/sbis.env
nano ~/.config/sbis/sbis.env
```

В редакторе заполни строки реальными значениями из карточки приложения:

```dotenv
SBIS_APP_CLIENT_ID=ВСТАВЬ_ID_ПРИЛОЖЕНИЯ
SBIS_APP_SECRET=ВСТАВЬ_ЗАЩИЩЕННЫЙ_КЛЮЧ
SBIS_SECRET_KEY=ВСТАВЬ_СЕРВИСНЫЙ_КЛЮЧ
```

В значениях не должно быть префикса `Bearer`, переносов строки или названий полей API. Не передавай ключи в чат и не сохраняй файл в репозитории.

Из каталога скилла выполни:

```bash
python3 scripts/sbis.py --env-file ~/.config/sbis/sbis.env check-env
python3 scripts/sbis.py --env-file ~/.config/sbis/sbis.env check
python3 scripts/sbis.py --env-file ~/.config/sbis/sbis.env organizations
```

Окружение процесса имеет приоритет над файлом, даже если переменная пустая. При первом обращении CLI получает токен и сохраняет его в приватном кэше. Успешный `check` возвращает `ok: true` и профиль; `organizations` показывает доступные организации. Проверь наличие нужной организации. Эти команды не создают документы.

Для службы или другого запускающего процесса настрой путь `--env-file` либо три переменные именно в его окружении. Настройки терминала не меняют окружение уже запущенной службы. Каталог кэша должен быть доступен пользователю, от имени которого выполняется CLI.

### 4. Получение токена и дальнейшее обслуживание

Вручную выпускать и подставлять токен для работы скилла не требуется. CLI отправляет три параметра на `https://online.sbis.ru/oauth/service/`, использует поле `token` ответа и добавляет его в `X-SBISAccessToken`. [Контракт сервисной авторизации](https://link.sbis.ru/page/kbase_entity/3033991d-f3da-41b6-9b8b-4c719df25e5a?folderId=b232dc93-97c9-4133-b999-7ac34ee58229).

Для ручной диагностики в Postman можно выполнить POST на этот адрес: Authorization — **No Auth**, Body — **raw / JSON**, заголовок `Content-Type: application/json`. Тело запроса:

```json
{
  "app_client_id": "ID_ПРИЛОЖЕНИЯ",
  "app_secret": "ЗАЩИЩЕННЫЙ_КЛЮЧ",
  "secret_key": "СЕРВИСНЫЙ_КЛЮЧ"
}
```

Успешный ответ содержит непустую строку `token`. Не вставляй её вместо одного из трёх ключей в env-файл: CLI принимает исходные параметры приложения. Ручной запрос создаёт отдельную сессию; по документации одновременно допускается не более пяти сессий приложения, затем старейшая завершается. Для обычной проверки используй `check` с переиспользованием кэша.

При `token_expired` клиент сбрасывает соответствующую запись кэша. Следующий безопасный `check` получит новый токен. Если администратор заменил ключи, обнови env-файл; изменённые параметры выберут новую запись кэша. При передаче через окружение обнови его у запускающего процесса. Клиент не отзывает прежние серверные сессии автоматически; при компрометации ключей закрой доступ старого подключения средствами Saby и настрой новые параметры.

| Ситуация | Что проверить |
|---|---|
| `credentials_required` | Все три значения заполнены; пустая переменная окружения не перекрывает файл. |
| `config_error` | Файл существует, доступен пользователю процесса и содержит корректные записи KEY=VALUE. |
| `token_expired` / HTTP 401 | Повтори безопасный `check`; при повторном отказе проверь параметры приложения и включённый сервисный доступ. |
| `access_denied` / HTTP 403 | Права приложения, организации, ограничения адресов и доступ к API по вашему тарифу. |
| `rpc_error` | Сервисный вход мог пройти, но метод ЭДО отказал; проверь права на конкретную операцию. |
| `network_error` | Доступ по HTTPS к хосту выбранного профиля, DNS, прокси и сетевые ограничения сервера. |

После изменения настроек проверь `check` и `organizations`. Перед повтором записи проверь состояние документа по [правилам восстановления](documents.md): автоматического повтора операции нет. Профиль `test` требует отдельной настройки доступа; сервисный вход на нём пока не проверен.

## Настройка CLI

Используется только сервисная авторизация приложения. Для каждого ключа CLI сначала читает переменную окружения; если она отсутствует — значение из `.env` текущего рабочего каталога. Пустая переменная окружения не заменяется значением из файла и приводит к `credentials_required` при обращении к API.

| Переменная | Назначение | Поле запроса API |
|---|---|---|
| `SBIS_APP_CLIENT_ID` | ID приложения | `app_client_id` |
| `SBIS_APP_SECRET` | Секрет приложения | `app_secret` |
| `SBIS_SECRET_KEY` | Сервисный ключ | `secret_key` |

Пример `.env` (заполни локально; не передавай секреты в чат):

```dotenv
SBIS_APP_CLIENT_ID=
SBIS_APP_SECRET=
SBIS_SECRET_KEY=
```

Окружение и `.env` можно сочетать: приоритет применяется отдельно к каждому ключу. CLI не меняет окружение процесса. Если все три переменные присутствуют в окружении, стандартный `.env` не читается. Отсутствующий стандартный файл допустим; недостающие или пустые обязательные значения блокируют сетевой запрос.

Глобальный аргумент `--env-file PATH` заменяет стандартный путь. Явно указанный файл читается даже при полном окружении; отсутствие файла, невозможность прочитать его или неверный синтаксис возвращают `config_error` без содержимого файла в диагностике.

Поддерживаются UTF-8, пустые строки, комментарии `#`, записи `KEY=VALUE`, пробелы вокруг `=` и значения в одинарных или двойных кавычках. Вне кавычек комментарий начинается с `#` в начале значения или после пробела; внутри кавычек `#` сохраняется. Значения однострочные и буквальные: команды, подстановки переменных и escape-последовательности не выполняются. Синтаксис `export KEY=VALUE` не поддерживается.

Примеры относительно каталога скилла (`.env` ищется в каталоге запуска):

```bash
python3 scripts/sbis.py check
python3 scripts/sbis.py --env-file /secure/sbis.env check
python3 scripts/sbis.py --profile test check
python3 scripts/sbis.py --timeout 120 organizations
python3 scripts/sbis.py --cache-dir /secure/sbis-cache check
```

Глобальные аргументы указываются перед командой. `check` вызывает `СБИС.СписокНашихОрганизаций` с пустым фильтром, возвращает только `ok` и профиль, без реквизитов организаций. Успех подтверждает доступ к этому методу, но не наличие организаций или права на остальные операции. `organizations` вызывает тот же метод и возвращает его результат, без автоматического обхода страниц. `СБИС.ИнформацияОТекущемПользователе` при живой проверке вернул HTTP 404 и для проверки доступа не используется. Профиль `test` — отдельный стенд, для него нужны собственные доступ и права.

## Контракт запросов

По [документации сервисной авторизации](https://link.sbis.ru/page/kbase_entity/3033991d-f3da-41b6-9b8b-4c719df25e5a?folderId=b232dc93-97c9-4133-b999-7ac34ee58229) клиент отправляет POST с тремя полями в JSON без обёртки JSON-RPC на `/oauth/service/`. Ответ должен содержать непустую строку `token`. В запросах ЭДО токен передаётся в `X-SBISAccessToken`; поля `access_token`, `sid` и заголовок `X-SBISSessionID` не используются.

| Профиль | Получение токена | Команды ЭДО |
|---|---|---|
| `production` | `https://online.sbis.ru/oauth/service/` | `https://online.sbis.ru/service/?srv=1` |
| `test` | `https://fix-online.sbis.ru/oauth/service/` | `https://fix-online.sbis.ru/service/?srv=1` |

Адреса ЭДО взяты из [технических требований](https://saby.ru/help/integration/api/techreq_edo). Адрес сервисного входа для `test` строится по хосту профиля и пока не подтверждён реальным запросом. Успешное получение токена само по себе не подтверждает доступность всех методов ЭДО: проверь `check` и доступные организации перед записью.

## Приватный кэш

Токен переиспользуется в памяти и сохраняется в `$XDG_CACHE_HOME/sbis/`, если `XDG_CACHE_HOME` задан абсолютным путём; иначе используется `~/.cache/sbis/`. Глобальный аргумент `--cache-dir PATH` задаёт сам каталог кэша и имеет приоритет над стандартным расположением. `XDG_CACHE_HOME` читается из окружения процесса, а не из `.env`. Имя файла — SHA-256 от версии формата, профиля и трёх параметров доступа. Каталог имеет права `0700`, файл — `0600`, замена атомарная. Исходные ключи в файл не записываются; смена любого ключа выбирает другую запись.

Кэш содержит действующий токен в открытом виде и должен оставаться приватным. Права рассчитаны на POSIX/Linux; на Windows дополнительно требуется ограничить ACL пользовательского каталога. При недоступном кэше клиент может продолжить работу с токеном в памяти и статическим предупреждением в stderr.

При HTTP 401 токен в памяти и соответствующий файл кэша сбрасываются; CLI возвращает `token_expired`. Автоматического повторения операции нет. Повтори безопасное чтение, чтобы получить новый токен. Перед повторной записью проверь состояние документа. Ошибки JSON-RPC с HTTP 200 также завершают команду без повторов и без анализа текста ошибки для выбора другого способа входа.

## Диагностика

Для остальных команд успех: JSON в stdout, код завершения `0`. Ошибка: JSON `{"error":{"code":"…","message":"…"}}` в stderr, код `1`; stdout пуст. `--help` выводит справку обычным текстом.

Основные коды: `credentials_required`, `config_error`, `token_expired`, `access_denied`, `rpc_error`, `http_error`, `network_error`, `invalid_response`. Секреты и токен маскируются в результатах; произвольные сообщения и трассировки сервера скрываются. CLI не принимает секреты аргументами командной строки и не печатает полученный токен.
